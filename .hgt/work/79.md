## Task (verbatim from the issue body)

## Context
The Actions executor can push a branch but `gh pr create` is rejected when "Allow GitHub
Actions to create and approve pull requests" is OFF — which §3 mandates (anti-rubber-stamp).
GitHub bundles create+approve into that one toggle (surfaced in #69, run 29973468423).
**Stopgap:** the toggle was flipped ON so the executor opens the PR as `github-actions[bot]`.
That's self-approval-safe — the bot authors the PR, and author≠reviewer (422) blocks any
Actions identity from approving it, so Carl's review is still the only one that counts. But
the flip leaves two costs on the table; this ticket buys them back.

## Scope
Open executor PRs as a **scoped machine-user token** (a write-access collaborator that is NOT
`github-actions` and NOT Carl) instead of `GITHUB_TOKEN`, and flip the toggle back OFF. Wire
it as the action's `github_token` (any token skips the App/OIDC path, so #57/#13 stay closed).
Two wins over the stopgap:
1. **CI runs on executor PRs.** `github-actions[bot]`-authored PRs don't trigger
   `on: pull_request` (#58); a machine-user-authored PR does.
2. **Toggle stays OFF.** ON is a repo-wide standing grant (§3 wanted it off): any workflow as
   `github-actions` could approve non-bot PRs. Machine-user creation removes the need.

Carl stays a clean third-party reviewer whose approval counts (#68/#60) — no #55 bypass.

## Token type — classic, not fine-grained (correction)
The original plan said a *fine-grained* PAT scoped to this repo. **That doesn't work:**
fine-grained PATs can only target repos the token's account **owns**, and the machine user is
a *collaborator* on `cesutherland/hgt` (owns nothing) — so the repo isn't selectable. Use a
**classic PAT scoped `public_repo` + `workflow`**:
- hgt is public → `public_repo` suffices and **can't touch private repos** (built-in containment),
- `workflow` is required to push `.github/workflows/**` changes.
The **GitHub App** is the cleaner endgame — short-lived install tokens, no resident PAT (#56/#68).
