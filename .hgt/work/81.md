## Context
#67 jails the `hgt work` session away from the operator's admin `gh` and `~/.ssh` (fail-closed).
But the deliverable is *open a PR*. The **original** #81 solved this with a creditless jail
+ a **host-side** `hgt work push <n>` verb (the operator's creds) for attended, and PAT-injection
only for unattended.

**Live pivot:** the sandbox uses the **scoped machine-user PAT — same as every other
execution surface** (the Actions executor's scoped `GITHUB_TOKEN`, the listener). Instead
of a creditless jail + a separate host publish step, the sandboxed session holds the scoped
credential via the `HGT_SANDBOX_GITHUB_TOKEN` seam + git-remote egress (#74) and
**publishes itself** — push branch, open/update PR — in both attended and unattended. One
identity model everywhere.

## Why this still respects the boundary
The publish boundary is preserved by **scope, not creditlessness**: the PAT is `contents` +
`pull-requests` write only — it can push feature branches and open PRs, and **cannot merge,
approve, write `main`, or act as admin** (branch protection + human merge gate hold). That's
exactly the "poor and powerless" posture (§2/§3) — powerless enough that holding the token
in the jail is fine. #67's "no admin `gh` / no `~/.ssh` / no host creds" stands; the jail
just also carries the scoped bot token, like the runner does.

## §3 tradeoff (naming it)
This puts a **persistent scoped credential in the attended local jail** — previously avoided
by publishing with the operator's host creds via a deliberate verb. The trade buys a unified
identity + hands-free publish; the cost is a resident bot PAT. Mitigated by: tight PAT scope
(contents+PR, no admin/merge/main), sandbox confinement (#67), and egress allowlisted to the
git remote (#74) so a leak reaches nothing else. An **App** with short-lived install tokens
is the cleaner endgame (identity thread, #56/#68).
